The instructor explains that the logic for finding a **Maximum Window** is fundamentally opposite to the logic for finding a **Minimum Window**. Understanding this inversion is crucial, as the standard template only works 50% of the time (for max windows).

## The Fundamental Difference: Maximum vs. Minimum Windows

When solving variable-sized sliding window problems, the required constraints will almost always correlate with the goal (Max vs. Min).

### Maximum Window Problems

- **Goal:** Find the `Longest` subarray/substring.
- **Condition:** `Sum <= K` or `Count <= K` (e.g., "At most K").
- **Why?** If the condition were `Sum >= K`, you could simply select the entire array and it would naturally be the longest window satisfying the condition.

### Minimum Window Problems

- **Goal:** Find the `Shortest` subarray/substring.
- **Condition:** `Sum >= K` or `Count >= K` (e.g., "At least K").
- **Why?** If the condition were `Sum <= K`, the shortest window would always be a single element (or an empty array), making the problem trivial.

##  Re-evaluating the Variable Window Template

In previous lectures (which focused heavily on Max Windows), the template was:

1. Move `high` to expand.
2. If the window is **INVALID**, move `low` to shrink it until it becomes valid.
3. Once valid, record the max length.

**Why this fails for Minimum Windows:**

Suppose you are looking for the shortest window where `Sum >= 80`.

- If your current sum is `30`, your window is **INVALID**.
- Should you shrink the window by moving `low`? **NO.** If you shrink, the sum will decrease further (e.g., to `10`), moving you further from your goal of `80`.
- You must _expand_ the window by moving `high` until the window becomes **VALID**.
- Once the window is **VALID** (e.g., sum is `120`), you record the length. _Then_ you shrink the window by moving `low` to see if a shorter window (e.g., sum of `90`) can still satisfy the condition.

##  Template: Minimum Sliding Window (The Inverted Logic)

For Minimum Windows, you shrink the window _while the condition is VALID_, continually updating the minimum length as you squeeze the window tighter.

### Pseudo-code: Minimum Sliding Window
```cpp
function minSlidingWindow(arr, target):
    n = length of arr
    low = 0
    result = infinity // Initialize to infinity to find minimum
    
    current_sum = 0
    
    // Step 1: Expand the window
    for high = 0 to n - 1:
        
        // Step 2: Include the 'high' element in your state/information
        current_sum = current_sum + arr[high]
        
        // Step 3: Shrink the window while the information is VALID
        while current_sum >= target:
            // Since it is valid, this is a potential answer. Record it!
            current_length = (high - low) + 1
            result = minimum(result, current_length)
            
            // Now shrink from the left to see if we can find a shorter valid window
            current_sum = current_sum - arr[low]
            low = low + 1
            
        // When the while loop exits, the window is INVALID. 
        // We do nothing here and let the for-loop expand 'high' again.
            
    // Return 0 if no valid window was ever found
    if result == infinity:
        return 0
        
    return result
```

## Side-by-Side Comparison

|**Feature**|**Maximum Window (Longest)**|**Minimum Window (Shortest)**|
|---|---|---|
|**Typical Condition**|`Value <= Target`|`Value >= Target`|
|**Initial Result Value**|`0` (or `-Infinity`)|`Infinity`|
|**When to Shrink (`low++`)?**|When the window is **INVALID**.|When the window is **VALID**.|
|**Goal of Shrinking**|To make the window valid again.|To find a smaller valid window.|
|**Where to record result?**|Outside the `while` loop (after it becomes valid).|Inside the `while` loop (before shrinking it).|

##  Active Recall

**Q: Why does a "Maximum Window" problem usually involve a "Less Than or Equal To" constraint (e.g., `Sum <= K`)?**
**A:** If a "Maximum Window" problem used a "Greater Than" constraint, the answer would almost always be the entire array, rendering the problem trivial and illogical. The constraint must act as a ceiling to limit the window's growth.

**Q: In the Minimum Sliding Window template, why do we trigger the inner `while` loop to shrink the window when the state is VALID, rather than invalid?**
**A:** If the state is invalid (e.g., current sum is lower than the required target), shrinking the window will only remove elements and lower the sum further, which does not help reach the target. We must wait until the state is valid, record the length, and _then_ shrink it to see if a shorter window can still satisfy the condition.

**Q: In the Maximum Sliding Window template, the result is updated _after_ the `while` loop. Why is the result updated _inside_ the `while` loop for the Minimum Sliding Window template?**
**A:** In a Max Window, the `while` loop runs while the state is invalid, so you must wait until it finishes (becomes valid) to record the answer. In a Min Window, the `while` loop runs while the state is valid, meaning every iteration of the loop represents a valid window that could be the new minimum length, so it must be recorded before the window is shrunk.
