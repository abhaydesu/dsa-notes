## Problem: Task Scheduler (LeetCode 621)

**Problem Statement:**

You are given a character array `tasks`, where each character represents a unique CPU task. You are also given an integer `n` that represents the cooling period between two **identical** tasks. This means that there must be at least `n` units of time between any two same tasks.

The CPU can execute one task per unit of time (or sit idle if no task can be executed). Return the **minimum number of units of time** that the CPU will take to finish all the given tasks.

**Example:**

- `tasks = ["A", "A", "A", "B", "B", "B"]`
    
- `n = 2` (Gap requirement)
    
- **Optimal Schedule:** `A -> B -> idle -> A -> B -> idle -> A -> B`
    
- **Output:** `8` units of time.
    

##  Intuition & Logic (The "PT Teacher Seating" Analogy)

Imagine you are a PT Teacher seating students for an exam. You have an infinite number of seats (time slots).

- **Rule:** Students from the same class must sit at least `n` seats apart to prevent cheating.
    

**Why Pure Alternation Fails Here:**

In "Reorganize String", if you had `A` and `B`, you could just do `A B A B`. But if the gap `n = 2`, `A B A` places the second `A` only 1 seat away from the first `A`. This is a violation. You _must_ leave an empty seat: `A B [idle] A`.

**The Greedy Strategy:**

Just like before, we must prioritize the task with the **highest remaining frequency**. Why? Because a high-frequency task requires the most "cooldown buffers". If we leave the highest-frequency task for the very end, we will have no other tasks left to execute during its cooldowns, forcing the CPU to sit idle for massive stretches of time.

### The Tracking Mechanism (The "Free Time" Registry)

We cannot simply pop the top task from a Max-Heap and place it. We must ensure its cooldown has expired.

To do this efficiently without scanning the array backwards, we maintain a registry (a Hash Map) called `freeTime`:

- `freeTime[Task]` = The absolute _minimum time slot_ (or seat number) at which this task is allowed to be scheduled again.
    
- Initially, every task can be scheduled at `time = 1`.
    
- If we schedule task `A` at `time = 1` and `gap = 2`, we update the registry: `freeTime[A] = time + gap + 1` $\rightarrow 1 + 2 + 1 = 4$. Next time we pop `A`, we cannot schedule it until at least `time = 4`.
    

## The Execution Flow

1. **Time Counter:** We start a variable `time = 1`. We increment this for every slot (whether we schedule a task or sit idle).
    
2. **The "Waiting Room" (Holding Queue):**
    
    - We pop the most frequent task from the Max-Heap.
        
    - We check the registry: Is `freeTime[Task] <= current_time`?
        
    - **If YES:** We schedule it! We decrement its frequency, update its `freeTime`, and if it still has remaining frequency, we push it back into the heap. We then increment the time and move to the next slot.
        
    - **If NO:** We _cannot_ schedule this task yet. It is still cooling down. We push it into a temporary "Waiting Room" list and pop the _next_ most frequent task from the heap.
        
3. **Idle Slots:**
    
    - If we pop everything out of the Max-Heap and _none_ of them are allowed to execute at the `current_time` (or the heap was completely empty but we still have tasks pending), it means the CPU _must_ sit idle for this time slot.
        
    - We increment `time++`.
        
4. **Reset:** Before moving to the next time slot, we take everything from the "Waiting Room" and push it back into the Max-Heap so it can be evaluated again for the new time slot.
    

## Pseudo-code: Task Scheduler

```cpp
function leastInterval(tasks, n):
    // Step 1: Frequency Map
    freqMap = empty HashMap
    for task in tasks:
        freqMap[task]++
        
    // Step 2: Registry to track when a task is free
    freeTime = empty HashMap
    for unique_task in freqMap:
        freeTime[unique_task] = 1 // All tasks are free at time 1
        
    // Step 3: Max-Heap of Pairs (Frequency, Task)
    maxHeap = empty Max-Heap
    for (task, freq) in freqMap:
        maxHeap.push(Pair(freq, task))
        
    time = 1 // Start at time slot 1
    
    // Step 4: Schedule tasks
    while not maxHeap.isEmpty():
        waiting_room = empty Array
        task_scheduled = false
        
        // Find the most frequent valid task for the current time slot
        while not maxHeap.isEmpty():
            current_task = maxHeap.top()
            maxHeap.pop()
            
            // Can we schedule it?
            if freeTime[current_task.task_name] <= time:
                // YES. Schedule it.
                current_task.freq--
                
                // If copies remain, update cooldown and put back in heap
                if current_task.freq > 0:
                    freeTime[current_task.task_name] = time + n + 1
                    maxHeap.push(current_task)
                    
                task_scheduled = true
                break // Stop searching this time slot
            else:
                // NO. It is on cooldown. Send to waiting room.
                waiting_room.push(current_task)
                
        // Return waiting tasks to the heap for future time slots
        for task in waiting_room:
            maxHeap.push(task)
            
        // Increment time (whether we scheduled a task or sat idle)
        time++
        
    // The loop increments time even after the last task is placed.
    // Subtract 1 to get the exact time units taken.
    return time - 1
```

## Complexity Analysis

- **Time Complexity:** $O(T \cdot \log K)$ where $T$ is the total time (including idle slots) and $K$ is the number of unique tasks.
    
    - $K \le 26$ (since tasks are uppercase English letters), so pushing/popping from the heap takes $O(1)$ effectively.
        
    - The outer loop runs $T$ times. The inner while loop pulls from the heap. In the worst case, it takes $O(T)$ time.
        
- **Space Complexity:** $O(1)$. The `freqMap`, `freeTime`, `maxHeap`, and `waiting_room` will store at most 26 elements, requiring constant $O(1)$ auxiliary space.
    

## Active Recall

**Q: Why is it crucial to update `freeTime[task] = time + n + 1` instead of `time + n`?**

**A:** If a task executes at `time = 1` and the required gap is `n = 2`, the next allowed execution time must leave exactly 2 empty slots. So, slots 2 and 3 are cooldowns. The task can only execute again at slot 4. Mathematically: $1 + 2 + 1 = 4$.

**Q: What happens when the inner `while` loop empties the Max-Heap but `task_scheduled` remains `false`?**

**A:** This indicates that all remaining tasks in the system are currently on cooldown for the `current_time` slot. Because no task can legally be scheduled, the CPU is forced to sit idle. The outer loop increments `time++`, and in the next iteration, the tasks pulled from the waiting room might now have their cooldowns expired.

**Q: Why is the final return value `time - 1` instead of just `time`?**

**A:** The `time` variable is aggressively incremented at the very bottom of the outer `while` loop. After the absolute last task is successfully scheduled and the heap becomes completely empty, the loop still increments `time` by 1 before checking the `while not maxHeap.isEmpty()` condition. Subtracting 1 corrects this final over-count.

**Q: In terms of the "Waiting Room" array, why do we return tasks to the heap immediately after placing one task, rather than waiting for their specific cooldowns to expire?**

**A:** The Max-Heap must always remain sorted purely by remaining frequency to maintain our greedy strategy. If we held tasks in a separate array until their cooldowns expired, we would have to manage time-based sorting alongside frequency sorting. By putting them back into the Max-Heap immediately, we ensure the heap naturally evaluates the highest-frequency tasks first in the _very next_ time slot, preserving the optimal greedy order without complex dual-sorting.
