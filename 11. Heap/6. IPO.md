## Problem: IPO (LeetCode 502)

**Problem Statement:**

Suppose LeetCode wants to start its IPO. In order to sell a good price of its shares to Venture Capitalists, LeetCode would like to work on some projects to increase its capital before the IPO.

You are given:

- `k`: The maximum number of distinct projects you can choose.
    
- `w`: Your initial capital.
    
- `profits`: An array where `profits[i]` is the profit of the $i^{th}$ project.
    
- `capital`: An array where `capital[i]` is the minimum capital required to start the $i^{th}$ project.
    

**Rule:** You can only pick a project if your current capital $W \ge capital[i]$. After finishing a project, its profit is _added_ to your total capital ($W = W + profit[i]$).

**Task:** Maximize your final capital after finishing at most `k` projects.

## Why Pure Sorting Fails

### Attempt 1: Sort by Maximum Profit

If we sort the projects strictly by profit descending, we might see a project offering $1,000,000$ profit at the top. But if its capital requirement is $50$ and our current capital $W$ is $10$, we can't start it. We would get stuck immediately.

### Attempt 2: Sort by Minimum Capital

If we sort the projects by minimum capital required ascending, we guarantee we pick projects we can afford.

- Let $W = 10$.
    
- Project 1: Cost = 1, Profit = 10
    
- Project 2: Cost = 3, Profit = 20
    
- Project 3: Cost = 8, Profit = 100
    
    If $k = 1$, picking the lowest capital project (Project 1) yields $10 + 10 = 20$ capital. But we _could_ have afforded Project 3, which yields $10 + 100 = 110$ capital!
    
    Purely picking the lowest cost project ignores the maximum available profit.
    

## Intuition & Logic (The "Dynamic Choices" Model)

We need a combination of both strategies.

1. We need to know _what we can afford_ at any given time.
    
2. Among everything we can afford, we must greedily pick the project that yields the _maximum profit_.
    
3. Because our capital $W$ only _grows_ (it never decreases), a project we can afford right now will **always** be affordable in the future. We never lose access to a project.
    

### The Algorithm

1. **Group and Sort:** Bind the `capital` and `profit` together into an array of Pairs. Sort this array ascendingly based strictly on **Capital**. (This allows us to process the cheapest projects first).
    
2. **Evaluate Choices:** As we iterate, if a project's capital requirement is $\le W$, it is an available "choice". We don't execute it immediately; instead, we put its **Profit** into a pool of available choices.
    
3. **Greedy Selection (The Heap):** To always pick the maximum profit from our available pool, that pool must be a **Max-Heap**.
    
4. **Execute:** Pop the top of the Max-Heap, add the profit to $W$. Now that $W$ has increased, more projects might have become available. Repeat the process up to `k` times.
    

## Pseudo-code: IPO

```cpp
function findMaximizedCapital(k, w, profits, capital):
    n = length of profits
    
    // Step 1: Create an array of pairs (Capital, Profit)
    projects = empty Array of Pairs
    for i = 0 to n - 1:
        projects.push( Pair(capital[i], profits[i]) )
        
    // Step 2: Sort the array ascending by Capital
    sort(projects)
    
    // Step 3: Max-Heap to store the profits of affordable projects
    maxHeap = empty Max-Heap
    idx = 0 // Pointer to track our position in the sorted projects array
    
    // Step 4: Try to pick k projects
    while k > 0:
        
        // Add all projects we can afford with our CURRENT capital to the heap
        while idx < n and projects[idx].capital <= w:
            maxHeap.push(projects[idx].profit)
            idx++ // Move to the next project
            
        // If the heap is empty, we cannot afford ANY more projects. 
        // We are bankrupt/stuck. Break early.
        if maxHeap.isEmpty():
            break
            
        // Greedily pick the project that gives the maximum profit
        w = w + maxHeap.top()
        maxHeap.pop()
        
        k-- // One project completed
        
    return w
```

## Complexity Analysis

- **Time Complexity:** $O(N \log N + K \log N)$.
    
    - Pairing and sorting the projects takes $O(N \log N)$ time.
        
    - In the worst case, we push all $N$ projects into the heap, which takes $O(N \log N)$ overall.
        
    - We pop from the heap $K$ times, taking $O(K \log N)$ time.
        
    - Overall Time Complexity simplifies to $O(N \log N)$.
        
- **Space Complexity:** $O(N)$.
    
    - We create an array of size $N$ to hold the pairs.
        
    - The Max-Heap can store up to $N$ elements in the worst case (if all projects require 0 capital).
        

## Active Recall

**Q: Why don't we need to worry about "losing" access to a project after we update $W$?**

**A:** The problem states that the profit is added to our initial capital, meaning $W$ only strictly increases or stays the same. If $W \ge capital[i]$ today, then $W + profit \ge capital[i]$ tomorrow. Therefore, once a project is pushed into the Max-Heap of affordable choices, it remains affordable forever, allowing us to safely defer executing it until it is the absolute best choice available.

**Q: In the main `while` loop, what does the condition `if maxHeap.isEmpty(): break` protect against?**

**A:** It protects against bankruptcy/stagnation. If we haven't completed $K$ projects yet, but our `maxHeap` is empty, it means our current capital $W$ is too low to afford the very next cheapest project in the sorted array. Since we have no projects to execute to increase our capital, we can never afford any remaining projects. We must break the loop and return our current capital.

**Q: Why does the algorithm use a `while` loop to push into the heap instead of just evaluating one project per $K$-iteration?**

**A:** Because increasing our capital might suddenly make _multiple_ new projects affordable at the same time. The inner `while` loop ensures that _every single_ project we can currently afford is added to the pool of choices before we ask the Max-Heap to give us the absolute best one.
